# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PolyBot: a Python bot for trading Polymarket's recurring 5-minute "Bitcoin Up or Down" markets, built around an "oracle lag" edge — Binance spot prices move continuously and lead the Chainlink-based oracle these markets resolve against, so watching Binance gives an early read on which way a window will close before Polymarket's own order book has repriced.

**Paper trading only.** All wallet, CLOB-auth, and order-placement code (`live_trader.py`, `order_executor.py`, `preflight_check.py`, `approve_usdc.py`, `createwallet/`, the dashboard's Live mode and wallet panel) was deliberately removed — it's in git history if ever needed. Don't reintroduce order placement unless the user explicitly asks.

No `pyproject.toml`/`setup.py` — dependencies live only in `.venv`, tracked via `requirements.txt` (see below).

## Architecture

Root-level scripts, each independently runnable, several importing from each other as plain modules:

- **`btc_price_feed.py`** — real-time BTC price from Binance's public WebSocket (trade/bookTicker/kline), with a REST-polling fallback if the socket drops.
- **`btc_5m_market_finder.py`** — discovers the live/upcoming Polymarket 5-min BTC markets. No API key needed.
- **`btc_15m_market_finder.py`** — same approach, one level up in recurrence: discovers Polymarket's 15-min BTC Up/Down series (`btc-updown-15m-<epoch>`, 900s windows). Reuses `resolve_market_outcome`/`fetch_order_book` from `btc_5m_market_finder.py` by import rather than duplicating them.
- **`oracle_lag_strategy.py`** — the strategy engine: Brownian-motion probability model + quarter-Kelly position sizing + hourly Telegram summaries. Imports the two scripts above. `--live` runs against real feeds but **only prints signals — it never places orders.**
- **`oracle_lag_strategy_v2.py`** — `OracleLagEngineV2`: the same probability/Kelly math as v1, reused by import (not duplicated), plus three additional entry filters ported from a reference bot ([JLowo/gengar_polymarket_bot](https://github.com/JLowo/gengar_polymarket_bot)) — an absolute probability floor (`--min-prob`), a multiplicative margin-of-safety filter (`--safety-factor`, distinct from v1's additive `--min-edge`), and a bounded entry time window (`--entry-window-start`/`--entry-window-end`, v1 has no lower bound at all). Same drop-in interface as v1. Kept as a separate engine (not an in-place change) so v1 stays runnable unchanged for comparison — select it via `--v2` on `paper_trader.py`, which defaults to v1.
- **`oracle_lag_strategy_v3.py`** — `OracleLagEngineV3(OracleLagEngineV2)`: subclasses v2 directly to inherit its filters unchanged, overriding only `compute()` to refresh `self.sizer.bankroll_usd` from an optional `bankroll_provider` callback (`set_bankroll_provider()`) before delegating to v2 — so Kelly sizing compounds off the caller's *current* bankroll instead of staying pinned to the fixed `--bankroll` value v1/v2 size against for the whole run. No provider wired = identical to v2 with a static bankroll (standalone `--live` mode never wires one). Select via `--v3` (mutually exclusive with `--v2`) on `paper_trader.py`, which wires it to `PaperTrader.equity()` — see the "Compounding bankroll design" gotcha below for why those callbacks return an *absolute* bankroll rather than a P&L delta.
- **`early_move_strategy.py`** — `EarlyMoveEngine(OracleLagEngine)`: enters only in the first ~90s of a window (`--early-min-elapsed`/`--early-max-elapsed`), and only when Binance has moved clearly away from the anchor — `|z| >= --min-z`, where `z = ln(last/anchor) / (sigma*sqrt(elapsed))`; sign(z) picks the side, so direction is never a coin flip. Skips windows with an approximate anchor (bot started mid-window), and asks above `--max-price` (book already repriced). **Fixed `--stake-usd` per trade** — no Kelly, never scales with bankroll. Subclasses v1 to reuse tick/anchor/vol/stats and v1's `evaluate()`; overrides only `compute()`. Select via `--early` on `paper_trader.py` (mutually exclusive with `--v2`/`--v3`); fourth panel (`early`) in `web_dashboard.py`.
- **`trend_strategy.py`** — experimental EMA-cross + Supertrend confirmation engine for the 5-min series, implementing the same `on_price_tick`/`set_market`/`compute`/`evaluate` interface as `oracle_lag_strategy.OracleLagEngine` so it's a drop-in swap. Driven by `experiments/trend_paper_trader.py`, which remains fully runnable standalone but is no longer wired into `web_dashboard.py` (see below) — that removal was UI-only; the script and its historical state/trades files were untouched.
- **`gabagool_strategy.py`** — `GabagoolEngine`: a YES/NO order-book arbitrage strategy on the 15-min series, ported from the "Gabagool" strategy in [minculusofia-wq/Apex-Predator](https://github.com/minculusofia-wq/Apex-Predator). Fundamentally different shape from the two engines above (no probability model, no direction, no Binance dependency at all — see its module docstring), so it does not implement their interface. Driven by `paper_trading/gabagool_paper_trader.py`.
- **`performance_tracker.py`** — schemas + `PerformanceTracker` class for three append-only CSV logs (`signals.csv`, `trades.csv`, `executions.csv`). Library only; wired in by `paper_trader.py`.
- **`notify.py`** — `send_telegram_message()`, the single Telegram sender used by every bot's hourly summary and by `watchdog.py`'s alerts. Loads `.env` itself so it works standalone. Best-effort: prints to stderr instead of raising if unconfigured or the API call fails.
- **`pidfile.py`** — tiny single-instance-protection helper (`claim_or_exit`, `pid_is_alive`, `read_pid`). Any long-running bot process should claim a pidfile on startup so a process-manager (or a human) can reliably tell "is this already running?" without holding a live subprocess handle — see `paper_trader.py`. `pid_is_alive` treats a zombie (exited, not yet reaped by its parent) as **not** alive — `os.kill(pid, 0)` alone would report a zombie as running, which is wrong for every caller here. Also owns the **autorestart marker** (`write_autorestart_marker` / `clear_autorestart_marker` / `read_autorestart_marker`) used by `watchdog.py` — see below.
- **`watchdog.py`** — polls whether `paper_trader.py` is alive and restarts + Telegram-alerts on an unexpected crash. See the dedicated section below.
- **`paper_trading/`** — home to two independent paper-trading loops (one runnable as v1/v2/v3) plus the one dashboard that manages all of them (restarting any one process never interrupts the others):
  - `paper_trader.py` runs the same live pipeline as `oracle_lag_strategy.py --live` but simulates fills against a virtual bankroll — no wallet, no CLOB auth, no funds at risk. Claims a pidfile (`paper_trader.pid`) on startup. `--v2`/`--v3` (mutually exclusive) swap in `oracle_lag_strategy_v2.OracleLagEngineV2` / `oracle_lag_strategy_v3.OracleLagEngineV3`; point `--state-file`/`--trades-log` at different files than a concurrent run of another version to A/B them without shared history.
  - `gabagool_paper_trader.py` — the Gabagool arbitrage loop (`gabagool_strategy.GabagoolEngine`, BTC 15-min series). Lives in this directory but shares no state, logic, or files with `paper_trader.py` — own state file (`gabagool_state.json`), trades log, and pidfile. Paper-only by design; see its module docstring. No longer wired into `web_dashboard.py` (UI-only removal, see below) — run it directly (`python paper_trading/gabagool_paper_trader.py`) or watch it with `dashboard.py`/its own state file.
  - `web_dashboard.py` — the Flask web UI (`:5000` by default), showing **three panels** — oracle-lag v1, v2, and v3. Reads each bot's state file/trades log from disk only; never imports or talks to any bot process directly. Also doubles as the **bot control plane** — see below.
  - `dashboard.py` — read-only terminal dashboard alternative (`rich`-based), reused by `web_dashboard.py` for its price-watching logic.
  - Because this subdirectory imports root-level modules, these scripts insert the project root onto `sys.path` before importing — preserve this pattern (see any of their top-of-file comments) if you add another script here or another subdirectory like it.

Run any script with `.venv/bin/python <script>.py --help` to see its flags — usage examples are in each script's module docstring, not repeated here.

## Bot control plane (`web_dashboard.py`)

`paper_trading/web_dashboard.py` is the single dashboard for `paper_trader.py` (v1, and via `--v2`/`--v3`, v2/v3) — three bots (`paper`/`oracle_v2`/`oracle_v3` in `BOT_SCRIPTS`), each spawned as its own subprocess (`/api/bot/start`, `/api/bot/stop`, `/api/bot/status`) and rendered as its own panel. All three are the same script pointed at entirely separate `--state-file`/`--trades-log`/`--pid-file`/`--autorestart-marker`/`--perf-log-dir` (see `_oracle_v2_args`/`_oracle_v3_args`, `ORACLE_V2_*`/`ORACLE_V3_*` constants) — that script's own defaults for all five are identical regardless of `--v2`/`--v3`, so every one of them has to be overridden explicitly or "oracle_v2"/"oracle_v3" would silently collide with "paper" (worst case: refuse to start at all, since pidfile.py can't tell them apart without a distinct `--pid-file`). `/api/data` returns all three paper states in one payload (`bots.paper`/`bots.oracle_v2`/`bots.oracle_v3`) rather than taking a `?strategy=` selector. It tells whether a bot is running by checking that bot's **pidfile** (`pidfile.py`), not by holding onto the `subprocess.Popen` handle — a dashboard restart would otherwise lose track of a still-running bot (or worse, spawn a duplicate on top of it). Keep `--host` at its `127.0.0.1` default — these endpoints start/stop processes and delete state, so don't expose them beyond localhost without treating that as a real access-control decision. `_bot_status` opportunistically calls `.poll()` on any `bot_processes` handle it holds, so a crashed child doesn't linger as a zombie between explicit stop calls.

`/api/<strategy>/reset` (one route for all of `PAPER_STRATEGIES`) **archives** (moves, never deletes) that bot's own state/trades files and perf-log CSVs into `paper_trading/archive/<strategy>-<UTC timestamp>/` — they're the data for analysing a run (refusing with 409 while that bot is running). An `early` bot (`paper_trader.py --early`, `_early_args`/`EARLY_*` constants) is a fourth entry in `BOT_SCRIPTS`/`PAPER_STRATEGIES`, same distinct-files treatment as v2/v3.

**Gabagool and `experiments/trend_paper_trader.py` used to have panels here too — both removed, UI-only.** `gabagool_strategy.py`, `gabagool_paper_trader.py`, `trend_strategy.py`, and `experiments/trend_paper_trader.py` are all untouched — none of their code, state files, or trade history were deleted, and each remains fully runnable standalone (`python paper_trading/gabagool_paper_trader.py`, `python experiments/trend_paper_trader.py`). Only removed from `web_dashboard.py`'s registries (`BOT_SCRIPTS`/`PAPER_STRATEGIES`/`ARGS_BUILDERS`/`_state_paths_for`) and their reset routes (`/api/gabagool/reset`, `/api/trend/reset`) and panels in `dashboard.html` — this dashboard now shows only the three oracle-lag versions,.

## Watchdog (`watchdog.py`)

Independent process (its own pidfile) that polls whether `paper_trader.py` is alive and, if it has gone down unexpectedly, restarts it with its last-known args and sends a Telegram alert via `notify.send_telegram_message`. Deliberately separate from `web_dashboard.py` — a watchdog crash shouldn't take a bot down, and a bot's ability to be resurrected shouldn't depend on the dashboard being up.

The one thing this has to get right: telling "crashed" apart from "the user meant to stop this" — resurrecting a bot someone deliberately stopped would undo the whole point of the Stop button. The bot writes an **autorestart marker** (`pidfile.write_autorestart_marker`) right after claiming their pidfile, and clear it **only** from the `except asyncio.CancelledError` branch in `main()` — i.e. only on a signal-triggered graceful shutdown (Ctrl+C, or the dashboard's Stop button sending SIGTERM). Any other exception path leaves the marker in place, since that's a real crash. So watchdog.py's rule is simple: marker present + pidfile dead → crashed, restart it; marker absent → intentionally stopped, leave it down. Do **not** move the marker-clearing call into a generic `finally`/`atexit` block — those also fire after an uncaught exception, which would erase the evidence a crash needs to be detected.

`--max-restarts-per-hour` (default 5) stops the watchdog from restart-looping a bot that immediately crashes every time — past the limit it sends one "needs manual attention" alert and stops trying, rather than repeatedly spamming Telegram. `trend_paper_trader.py` and `gabagool_paper_trader.py` are not wired into `watchdog.py`'s `BOT_SCRIPTS` (neither has needed autorestart supervision yet — add either explicitly if that changes).

## Telegram notifications are version-labeled

`HourlyStatsTracker.build_summary()` (`oracle_lag_strategy.py`) takes an optional `version_label` param (default `"Oracle-lag scalper"`, reproducing v1's original text byte-for-byte so v1's messages are unchanged) that's threaded through the summary's title line. `OracleLagEngineV2`/`V3` pass `stats_label="Oracle-lag scalper v2"`/`"...v3"` into their `HourlyStatsTracker` at construction, so hourly Telegram summaries are distinguishable by version without changing v1's output. The actual send goes through `notify.send_telegram_message`.

## Testing convention

There is no unit test suite (no `test_*.py` files). The established convention instead: **verify by actually running the script against real endpoints** — Binance, Polymarket's Gamma API — not mocked tests. Keep following this convention for new scripts unless the user asks for real unit tests.

`oracle_lag_strategy.py --selftest`, `oracle_lag_strategy_v2.py --selftest`, `oracle_lag_strategy_v3.py --selftest`, `early_move_strategy.py --selftest`, and `gabagool_strategy.py --selftest` are the exceptions — synthetic, no-network sanity checks of the probability/Kelly math, the v2 entry-filter math, the v3 compounding-bankroll math (stake scales up after a simulated win, down after a loss, floors at 0 for a negative bankroll), and the fee-aware arbitrage sizing math, respectively. A real (non-synthetic) parallel v1+v2+v3 paper run against live Binance/Polymarket feeds proves the plumbing doesn't crash and every engine reaches the same live market data — it does *not* prove compounding itself (that needs enough closed trades to move the bankroll, which a short smoke run won't produce); the `--selftest` is the actual proof of the compounding math.

## Key gotchas

- **5-minute market discovery** (`btc_5m_market_finder.py`): Polymarket appears to batch pre-create a full day's worth of future 5-min windows in advance. Asking Gamma for "most recently created" markets surfaces *tomorrow's* freshly-created placeholder windows, not today's genuinely-about-to-close one. The fix already in place: compute the expected slug (`btc-updown-5m-<epoch>`, epoch always a multiple of 300) directly from wall-clock time and look it up, rather than sorting/filtering a list. Also: don't trust Gamma's `closed` flag for these fast-cycling markets — it lags actual resolution; status is derived from epoch vs. wall clock instead.
- **Zero-drift probability model** (`oracle_lag_strategy.py`): the Brownian-motion model deliberately assumes zero drift. Over a 5-minute horizon, real trend is swamped by noise, and zero drift keeps the estimate a pure martingale with no built-in directional bias — the actual edge comes from seeing the price before the market/oracle does, not from predicting direction.
- **Realized vol is sampled per second, not per tick** (`RollingVolatilityEstimator.sigma_per_sqrt_sec`): Binance prints most trades in same-millisecond bursts, and the old tick-to-tick version skipped `dt == 0` pairs, silently dropping the price changes inside them. Measured live at ~3%/yr for BTC (real: ~20-25%), so a 15bp move read as p_up=1.0 while the book sat at 0.51. The per-second version matches Binance's own 1s klines exactly. Every signal logged before this fix used the broken sigma; don't mix it into analysis.
- **Quarter-Kelly default**: `kelly_multiplier=0.25` is deliberate, not conservative-for-its-own-sake — the probability model is an approximation, not a known-true probability, so full Kelly would be overconfident. `max_position_pct` is a separate hard cap independent of what Kelly suggests.
- **Trade settlement source of truth**: `paper_trader.py` prefers Polymarket's own Gamma API resolution (`outcomePrices`) over the bot's own price-based guess. Only falls back to comparing last-known price to the window anchor after `SETTLE_FALLBACK_AFTER` (1 hour — Gamma's real resolution was measured landing 6-10+ min after close, so the old 120s turned nearly every settlement into a guess) with no Gamma resolution — and flags that fallback explicitly (`resolution_source: "price-fallback"` vs `"gamma"`) so it's never silently conflated with a real settlement.
- **`trades.csv` is a post-trade blotter, not a lifecycle log**: one row per trade, appended only once it resolves (entry+fill+exit+resolution together). Open positions are visible live via `paper_state.json` instead — don't try to append an "OPEN" row to `trades.csv` for a new trade type; follow the existing pattern.
- **`.env`** is loaded automatically by scripts that need it (via `python-dotenv`, resolved relative to the project root regardless of cwd) — real environment variables still take precedence over it.
- **`resolve_market_outcome()` lives in `btc_5m_market_finder.py`**, not in `paper_trader.py` — every bot imports and calls the same function so settlement logic can't silently drift between them. Add any future settlement-source changes there once, not per-bot.
- **Pidfile-based single-instance protection**: `paper_trader.py` calls `pidfile.claim_or_exit()` at startup and exit immediately if another instance is already alive per their pidfile. Two paper bots sharing one state file would corrupt it.
- **Paper fills use the live CLOB book, not Gamma**: `paper_trader.py` prices each side from its own token's best ask (`finder.fetch_best_ask`). Gamma's `bestAsk` was measured lagging the real book, and `1 - up_bid` is only an approximation of Down's real cost.
- **Order book ask ordering** (`/book` from `clob.polymarket.com`): `asks` comes back sorted **descending** (worst price first, best/lowest price last) — the opposite of what a naive `asks[:N]` read would assume, and the opposite of `bids`' own ordering (ascending). `gabagool_strategy.py`'s book-walking code re-sorts explicitly rather than trusting response order; check this again if you write anything else that reads `/book` directly.
- **Gabagool's fee formula is load-bearing, not a footnote**: `fee = shares * fee_rate * price * (1 - price)`, taker-only, `fee_rate = 0.07` for crypto-category markets — verified against `docs.polymarket.com/trading/fees.md` and the live `/fee-rate` endpoint, not assumed from the reference repo's threshold. This fee is symmetric around 50¢ and *maximized* there, which is exactly where a crossed book is most likely to appear — a fee-blind "sum < $0.975" filter (the reference repo's own rule) can and does approve trades that are a guaranteed net loss. If this fee schedule ever changes, `gabagool_strategy.py`'s `--fee-rate` flag needs updating, not just its default.
- **`gabagool_paper_trader.py` lives in `paper_trading/`, not its own directory**: it was originally built as a fully siloed `gabagool_bot/` bot with its own dashboard, then folded in once `web_dashboard.py` grew to manage multiple paper strategies in parallel (later removed from that dashboard again — UI-only, see "Bot control plane" above — but left in this directory rather than moved back out, since nothing about where the file lives depends on whether the dashboard currently renders it). It still shares no state or logic with `paper_trader.py`: separate state file, trades log, and pidfile, and a completely different (non-Kelly, non-directional) engine.
- **Additive vs. multiplicative entry filters are genuinely different math, not two names for the same thing**: v1's `--min-edge` is additive (`p_true - price >= threshold`); v2's `--safety-factor` is multiplicative (`price <= p_true * factor`). They diverge sharply away from p=0.5 — at p=0.90, `min_edge=0.02` allows paying up to 0.88, but `safety_factor=0.85` only allows paying up to 0.765. Don't conflate them when reasoning about either engine's behavior, and don't assume tightening one tightens the other.
- **Compounding bankroll design (`oracle_lag_strategy_v3.py`)**: `OracleLagEngineV3.set_bankroll_provider()` deliberately takes a callback returning the caller's **absolute** current bankroll, not a P&L delta to add to the initial value. Reason: `PaperTrader.stats()['realized_pnl']` is summed from an in-memory `closed_positions` list that, on process restart, is rebuilt only from the state file's capped `recent_closed` tail (last 25) — a delta fed by that figure would silently understate the true bankroll after any restart following more than 25 closed trades. `PaperTrader.equity()` (`cash` + open-position stakes) sidesteps this entirely since `cash` is restored verbatim from the state file, so `paper_trader.py` wires `engine.set_bankroll_provider(trader.equity)` directly. Bankroll is floored at 0 before being handed to `KellySizer` either way, so a provider that (temporarily) returns negative never produces a negative stake.
