# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PolyBot: a Python bot for trading Polymarket's recurring 5-minute "Bitcoin Up or Down" markets, built around an "oracle lag" edge — Binance spot prices move continuously and lead the Chainlink-based oracle these markets resolve against, so watching Binance gives an early read on which way a window will close before Polymarket's own order book has repriced.

No `pyproject.toml`/`setup.py` — dependencies live only in `.venv`, tracked via `requirements.txt` (see below).

## Architecture

Root-level scripts, each independently runnable, several importing from each other as plain modules:

- **`btc_price_feed.py`** — real-time BTC price from Binance's public WebSocket (trade/bookTicker/kline), with a REST-polling fallback if the socket drops.
- **`btc_5m_market_finder.py`** — discovers the live/upcoming Polymarket 5-min BTC markets. No API key needed.
- **`btc_15m_market_finder.py`** — same approach, one level up in recurrence: discovers Polymarket's 15-min BTC Up/Down series (`btc-updown-15m-<epoch>`, 900s windows). Reuses `resolve_market_outcome`/`fetch_order_book` from `btc_5m_market_finder.py` by import rather than duplicating them.
- **`oracle_lag_strategy.py`** — the strategy engine: Brownian-motion probability model + quarter-Kelly position sizing + hourly Telegram summaries. Imports the two scripts above. `--live` runs against real feeds but **only prints signals — it never places orders.**
- **`oracle_lag_strategy_v2.py`** — `OracleLagEngineV2`: the same probability/Kelly math as v1, reused by import (not duplicated), plus three additional entry filters ported from a reference bot ([JLowo/gengar_polymarket_bot](https://github.com/JLowo/gengar_polymarket_bot)) — an absolute probability floor (`--min-prob`), a multiplicative margin-of-safety filter (`--safety-factor`, distinct from v1's additive `--min-edge`), and a bounded entry time window (`--entry-window-start`/`--entry-window-end`, v1 has no lower bound at all). Same drop-in interface as v1. Kept as a separate engine (not an in-place change) so v1 stays runnable unchanged for comparison — select it via `--v2` on `paper_trader.py` or `live_trader.py`, both of which default to v1.
- **`oracle_lag_strategy_v3.py`** — `OracleLagEngineV3(OracleLagEngineV2)`: subclasses v2 directly to inherit its filters unchanged, overriding only `compute()` to refresh `self.sizer.bankroll_usd` from an optional `bankroll_provider` callback (`set_bankroll_provider()`) before delegating to v2 — so Kelly sizing compounds off the caller's *current* bankroll instead of staying pinned to the fixed `--bankroll` value v1/v2 size against for the whole run. No provider wired = identical to v2 with a static bankroll (standalone `--live` mode never wires one). Select via `--v3` (mutually exclusive with `--v2`) on `paper_trader.py`/`live_trader.py`, which wire it to `PaperTrader.equity()` / `LiveTrader.equity()` respectively — see the "Compounding bankroll design" gotcha below for why those callbacks return an *absolute* bankroll rather than a P&L delta.
- **`trend_strategy.py`** — experimental EMA-cross + Supertrend confirmation engine for the 5-min series, implementing the same `on_price_tick`/`set_market`/`compute`/`evaluate` interface as `oracle_lag_strategy.OracleLagEngine` so it's a drop-in swap. Driven by `experiments/trend_paper_trader.py`, which remains fully runnable standalone but is no longer wired into `web_dashboard.py` (see below) — that removal was UI-only; the script and its historical state/trades files were untouched.
- **`gabagool_strategy.py`** — `GabagoolEngine`: a YES/NO order-book arbitrage strategy on the 15-min series, ported from the "Gabagool" strategy in [minculusofia-wq/Apex-Predator](https://github.com/minculusofia-wq/Apex-Predator). Fundamentally different shape from the two engines above (no probability model, no direction, no Binance dependency at all — see its module docstring), so it does not implement their interface. Driven by `paper_trading/gabagool_paper_trader.py`.
- **`order_executor.py`** — places/cancels real CLOB orders via `py_clob_client`. Owns credential loading (`load_private_key`, `build_client`) that other scripts reuse.
- **`preflight_check.py`** — read-only pre-trade checks (wallet balances, CLOB auth levels, USDC allowances). Imports credential loading from `order_executor.py`.
- **`approve_usdc.py`** — sends real on-chain `approve()` transactions granting Polymarket's exchange contracts a USDC allowance. Also imports from `order_executor.py`.
- **`performance_tracker.py`** — schemas + `PerformanceTracker` class for three append-only CSV logs (`signals.csv`, `trades.csv`, `executions.csv`). Library only; wired in by `paper_trader.py` and `live_trader.py`.
- **`pidfile.py`** — tiny single-instance-protection helper (`claim_or_exit`, `pid_is_alive`, `read_pid`). Any long-running bot process should claim a pidfile on startup so a process-manager (or a human) can reliably tell "is this already running?" without holding a live subprocess handle — see `paper_trader.py` and `live_trader.py`. `pid_is_alive` treats a zombie (exited, not yet reaped by its parent) as **not** alive — `os.kill(pid, 0)` alone would report a zombie as running, which is wrong for every caller here. Also owns the **autorestart marker** (`write_autorestart_marker` / `clear_autorestart_marker` / `read_autorestart_marker`) used by `watchdog.py` — see below.
- **`watchdog.py`** — polls whether `paper_trader.py` / `live_trader.py` are alive and restarts + Telegram-alerts on an unexpected crash. See the dedicated section below.
- **`createwallet/create_polygon_wallet.py`** — standalone, generates a new Polygon wallet.
- **`paper_trading/`** — home to two independent paper-trading loops (one runnable as v1/v2/v3) plus the one dashboard that manages all of them (restarting any one process never interrupts the others):
  - `paper_trader.py` runs the same live pipeline as `oracle_lag_strategy.py --live` but simulates fills against a virtual bankroll — no wallet, no CLOB auth, no funds at risk. Claims a pidfile (`paper_trader.pid`) on startup. `--v2`/`--v3` (mutually exclusive) swap in `oracle_lag_strategy_v2.OracleLagEngineV2` / `oracle_lag_strategy_v3.OracleLagEngineV3`; point `--state-file`/`--trades-log` at different files than a concurrent run of another version to A/B them without shared history.
  - `gabagool_paper_trader.py` — the Gabagool arbitrage loop (`gabagool_strategy.GabagoolEngine`, BTC 15-min series). Colocated here so the same dashboard manages it, but shares no state, logic, or files with `paper_trader.py` — own state file (`gabagool_state.json`), trades log, and pidfile. Paper-only by design; see its module docstring.
  - `web_dashboard.py` — the Flask web UI (`:5000` by default), showing **four strategy panels side by side** (oracle-lag v1, oracle-lag v2, oracle-lag v3, Gabagool) plus the live-trading panel. Reads each bot's state file/trades log from disk only; never imports or talks to any bot process directly. Also doubles as the **bot control plane** — see below.
  - `dashboard.py` — read-only terminal dashboard alternative (`rich`-based), reused by `web_dashboard.py` for its price/wallet-watching logic.
  - Because this subdirectory imports root-level modules, these scripts insert the project root onto `sys.path` before importing — preserve this pattern (see any of their top-of-file comments) if you add another script here or another subdirectory like it.
- **`live_trading/live_trader.py`** — the real-money counterpart to `paper_trader.py`. See the dedicated section below before touching this file; its safety model is deliberately different from the rest of the codebase.

Run any script with `.venv/bin/python <script>.py --help` to see its flags — usage examples are in each script's module docstring, not repeated here.

## Bot control plane (`web_dashboard.py`)

`paper_trading/web_dashboard.py` is the single dashboard for every bot in this repo: `paper_trader.py` (v1, and via `--v2`/`--v3`, v2/v3), `gabagool_paper_trader.py`, and `live_trading/live_trader.py` (v1, and via `--v2`/`--v3`, v2/v3), each spawned as its own subprocess (`/api/bot/start`, `/api/bot/stop`, `/api/bot/status`) and shown as its own always-visible panel — **not** a toggle between strategies; all four paper strategies (`paper`/`oracle_v2`/`oracle_v3`/`gabagool` in `BOT_SCRIPTS`) run and render in parallel, independently start/stop-able, so you can compare them live against the same market instead of switching between them. `paper`, `oracle_v2`, and `oracle_v3` are the same script (`paper_trader.py --v2`/`--v3`) pointed at entirely separate `--state-file`/`--trades-log`/`--pid-file`/`--autorestart-marker`/`--perf-log-dir` (see `_oracle_v2_args`/`_oracle_v3_args`, `ORACLE_V2_*`/`ORACLE_V3_*` constants) — that script's own defaults for all five are identical regardless of `--v2`/`--v3`, so every one of them has to be overridden explicitly or "oracle_v2"/"oracle_v3" would silently collide with "paper" (worst case: refuse to start at all, since pidfile.py can't tell them apart without a distinct `--pid-file`). `/api/data` returns all four paper states in one payload (`bots.paper`/`bots.oracle_v2`/`bots.oracle_v3`/`bots.gabagool`) rather than taking a `?strategy=` selector. It tells whether a bot is running by checking that bot's **pidfile** (`pidfile.py`), not by holding onto the `subprocess.Popen` handle — a dashboard restart would otherwise lose track of a still-running bot (or worse, spawn a duplicate on top of it). Starting `mode` in `LIVE_STRATEGIES` (`"live"`/`"live_v2"`/`"live_v3"`) always re-runs `preflight_check.py`'s full check set first and refuses with HTTP 412 if it isn't READY; there is no way to skip that from the dashboard for any of the three — and this dashboard-level gate is a backstop only, since `live_trader.py`'s own `run_preflight_gate()` reruns the identical checks again inside the subprocess before it ever trades, so a bug in the dashboard's gate can block a start but never cause an unsafe one. Keep `--host` at its `127.0.0.1` default for this script specifically — these endpoints can start a live-money bot, so don't expose them beyond localhost without treating that as a real access-control decision. `_bot_status` opportunistically calls `.poll()` on any `bot_processes` handle it holds, so a crashed child doesn't linger as a zombie between explicit stop calls.

`/api/paper/reset`, `/api/oracle_v2/reset`, `/api/oracle_v3/reset`, and `/api/gabagool/reset` each delete only their own bot's state/trades files (refusing with 409 while that bot is running). Deliberately no reset endpoint exists for `live`/`live_v2`/`live_v3` — wiping a real trade history isn't something to expose as a dashboard button.

**Live mode toggle on the oracle_v2/oracle_v3 panels**: each of those two paper panels has a Paper/Live mode switch (v1's paper panel doesn't — it already has a full live-trading control via the separate "Live Trading" section, so the toggle would just be a redundant second entry point to the same `live` bot). Flipping a panel to Live changes what its Start button targets — `live_v2`/`live_v3` instead of `oracle_v2`/`oracle_v3` — reusing the exact same preflight-check + typed-"START LIVE"-confirmation flow as the standalone v1 live panel, just parameterized per panel (`checkPreflightFor`/`showLiveConfirmFor`/`confirmStartLiveFor` in `dashboard.html`, mirroring `checkPreflight`/`showLiveConfirm`/`confirmStartLive`). Bankroll/min-edge/max-position-pct/kelly-multiplier/min-prob/safety-factor/entry-window fields are shared between a panel's Paper and Live modes (same strategy parameters either way, just simulated vs. real order placement); only the live-only caps (`max-stake-usd`/`max-trades-per-hour`/`max-trades-per-day`/`max-open-positions`/`max-daily-loss-usd`) are separate fields, shown only in Live mode. `/api/data`'s `"live_bots"` key (`live`/`live_v2`/`live_v3`, via `LIVE_STRATEGIES`/`_live_state_paths_for`) surfaces live state read-only for display — a different JSON shape from the paper `"bots"` key (`LiveTrader._write_state` has no `cash`/`equity`/`starting_bankroll`, but does have a `caps` block with the circuit-breaker/loss-guard/ghost-fill-halt flags), so `dashboard.html` renders it with a dedicated `renderLivePanel()` rather than reusing `renderDirectionalPanel()`.

`experiments/trend_paper_trader.py` (EMA/Supertrend confirmation) used to have a panel here too and has since been removed from the dashboard's registries (`BOT_SCRIPTS`/`PAPER_STRATEGIES`/`ARGS_BUILDERS`/`_state_paths_for`, plus its `/api/trend/reset` route) in favor of the `oracle_v3` panel — that removal was **UI-only**: the script itself, its state file, and its trades log were never touched and it remains fully runnable standalone (`python experiments/trend_paper_trader.py`), just no longer visible or start/stop-able from this dashboard.

## Watchdog (`watchdog.py`)

Independent process (its own pidfile) that polls whether `paper_trader.py` / `live_trader.py` are alive and, if one has gone down unexpectedly, restarts it with its last-known args and sends a Telegram alert via `oracle_lag_strategy.send_telegram_message`. Deliberately separate from `web_dashboard.py` — a watchdog crash shouldn't take a bot down, and a bot's ability to be resurrected shouldn't depend on the dashboard being up.

The one thing this has to get right: telling "crashed" apart from "the user meant to stop this," especially once it's watching `live_trader.py` — resurrecting a bot someone deliberately stopped would undo the whole point of the Stop button. Both bots write an **autorestart marker** (`pidfile.write_autorestart_marker`) right after claiming their pidfile, and clear it **only** from the `except asyncio.CancelledError` branch in `main()` — i.e. only on a signal-triggered graceful shutdown (Ctrl+C, or the dashboard's Stop button sending SIGTERM). Any other exception path leaves the marker in place, since that's a real crash. So watchdog.py's rule is simple: marker present + pidfile dead → crashed, restart it; marker absent → intentionally stopped, leave it down. Do **not** move the marker-clearing call into a generic `finally`/`atexit` block — those also fire after an uncaught exception, which would erase the evidence a crash needs to be detected.

`--max-restarts-per-hour` (default 5) stops the watchdog from restart-looping a bot that immediately crashes every time (e.g. a live bot that's lost its USDC allowance will pass its own preflight-fail exit every restart) — past the limit it sends one "needs manual attention" alert and stops trying, rather than repeatedly hammering the CLOB and spamming Telegram. `trend_paper_trader.py` and `gabagool_paper_trader.py` are not wired into `watchdog.py`'s `BOT_SCRIPTS` (neither has needed autorestart supervision yet — add either explicitly if that changes).

## Telegram notifications are version-labeled

`HourlyStatsTracker.build_summary()` (`oracle_lag_strategy.py`) takes an optional `version_label` param (default `"Oracle-lag scalper"`, reproducing v1's original text byte-for-byte so v1's messages are unchanged) that's threaded through the summary's title line. `OracleLagEngineV2`/`V3` pass `stats_label="Oracle-lag scalper v2"`/`"...v3"` into their `HourlyStatsTracker` at construction, so hourly Telegram summaries are distinguishable by version without changing v1's output. `LiveTrader`'s ghost-fill alert (`_verify_no_ghost_fill`) is separately tagged via a `version_label` constructor param (`"v1"`/`"v2"`/`"v3"`, set in `live_trader.py`'s `run()`) since that alert doesn't go through `HourlyStatsTracker` at all.

## The safety pattern — required for any new money-touching script

`order_executor.py` and `approve_usdc.py` each independently implement the same pattern for anything that spends money or sends a real transaction. Follow it for any new script in this category:

- Default to a **dry run** that prints exactly what would happen (`mode=DRY RUN`), with no network mutation.
- Require an explicit **`--live`** flag to actually submit/broadcast.
- Even with `--live`, require a **typed "yes" confirmation** per action unless **`--yes`** is also passed.
- Never accept a private key via CLI argument (shell history, `ps` exposure) — only via `--private-key-env VAR` (env var name) or `--keystore PATH` (encrypted, password-prompted). Reuse `order_executor.load_private_key` rather than reimplementing this.
- API/session credentials are derived fresh each run, never cached to disk.

**Naming collision to watch for**: `oracle_lag_strategy.py --live` means "run against live data feeds" and is still read-only (no orders placed). `order_executor.py --live` and `approve_usdc.py --live` mean "actually submit a real transaction." Same flag name, very different consequences — don't assume `--live` is safe just because it is in one script.

### The one deliberate exception: `live_trading/live_trader.py`

This script *is* live trading by definition (there's no separate `--live` flag) — it's meant to run unattended from the dashboard's Start button, so a per-trade `input()` confirmation would just hang forever on a closed stdin. Confirmation is replaced with caps, not removed:

- **`preflight_check.py` must return READY before this process starts trading at all** — reused directly via `preflight_check.run_all_checks()`, not reimplemented, and not skippable via any flag. If you add a new preflight section, `live_trader.py`'s gate picks it up automatically.
- **`--max-stake-usd`** is a hard per-trade cap enforced through `order_executor.check_market_order` (the same risk check `order_executor.py` itself uses) — Kelly sizing is clamped down to this, never allowed to exceed it.
- **`--max-trades-per-hour` / `--max-trades-per-day`** (`RateLimiter`) is a circuit breaker independent of signal quality.
- **`--max-daily-loss-usd`** (`DailyLossGuard`) is an *optional*, off-by-default cumulative stop-loss — the three caps above bound risk per trade and per hour but not total daily drawdown.
- **`ClobHealthBreaker`** pings `client.get_ok()` immediately before every real order submission (not on every poll — only when a trade is actually about to happen) and halts new trades after `--clob-max-consecutive-failures` in a row (default 3), auto-resuming the moment a check succeeds again. Deliberately does **not** mark the market slug as traded on a trip, unlike the other guards above — a CLOB outage is worth retrying within the same window, not giving up on for the full 5 minutes.
- **Ghost-fill detection** (`LiveTrader._verify_no_ghost_fill`): if `submit_live_market_order` raises an exception, a network/API failure does **not** prove the order didn't fill on-chain anyway. This re-checks the real USDC balance against a pre-trade snapshot; a meaningful drop with no matching recorded position halts **all** further trading (`ghost_fill_halted` — does *not* auto-resume, unlike `ClobHealthBreaker`) and sends a Telegram alert, rather than guessing at reconstructing the phantom position. Scope limit: this detects that a fill likely happened, not what it was — recovering/reconciling the actual position still needs a human checking Polymarket directly.
- Order submission reuses `order_executor`'s `create_market_order`/`post_order` call directly (the exact signing path `order_executor.py` itself already exercises) rather than reimplementing signing — see `submit_live_market_order()`. It deliberately does **not** go through `order_executor.place_market_order`, whose `confirm_or_abort()` calls `input()`. (A reference bot this was compared against warned of float-precision bugs breaking order construction from naive `1 - price` arithmetic — verified directly against this repo's pinned `py_clob_client==0.34.6` that its own amount-rounding already corrects for this before the final `int()` conversion; no code change was needed.)
- Scope limit: `live_trader.py` tracks and reports positions (polling Gamma resolution, same as `paper_trader.py`) but does **not** redeem/claim winning conditional-token positions on-chain — that's still a separate manual step. `pnl_usd` there is an accounting estimate, not a confirmed on-chain settlement.
- `--v2`/`--v3` (mutually exclusive) swap in `oracle_lag_strategy_v2.OracleLagEngineV2` / `oracle_lag_strategy_v3.OracleLagEngineV3` (same as `paper_trader.py`'s `--v2`/`--v3`) — `ClobHealthBreaker`/ghost-fill detection apply either way, since they're execution-layer, not signal-layer. `--v3` wires `engine.set_bankroll_provider(trader.equity)` after construction (see the "Compounding bankroll design" gotcha below).

If you extend this script, keep it unattended-safe: no `input()`, no prompt that blocks on stdin, and no way to bypass the preflight gate.

## Testing convention

There is no unit test suite (no `pytest` usage despite `pytest` being installed, no `test_*.py` files). The established convention instead: **verify by actually running the script against real endpoints** — Binance, Polymarket's Gamma/CLOB APIs — not mocked tests. For anything that touches real funds, verify with a disposable throwaway wallet (`eth_account.Account.create()`) that has zero balance, so you can confirm the full request/signing/submission path reaches the real API and fails for the *expected* reason (e.g. insufficient balance, geoblock) rather than a bug in the code. Keep following this convention for new scripts unless the user asks for real unit tests.

`oracle_lag_strategy.py --selftest`, `oracle_lag_strategy_v2.py --selftest`, `oracle_lag_strategy_v3.py --selftest`, and `gabagool_strategy.py --selftest` are the exceptions — synthetic, no-network sanity checks of the probability/Kelly math, the v2 entry-filter math, the v3 compounding-bankroll math (stake scales up after a simulated win, down after a loss, floors at 0 for a negative bankroll), and the fee-aware arbitrage sizing math, respectively. A real (non-synthetic) parallel v1+v2+v3 paper run against live Binance/Polymarket feeds proves the plumbing doesn't crash and every engine reaches the same live market data — it does *not* prove compounding itself (that needs enough closed trades to move the bankroll, which a short smoke run won't produce); the `--selftest` is the actual proof of the compounding math. `live_trader.py`'s new `ClobHealthBreaker`/ghost-fill logic was verified the same way this repo verifies everything else touching real state: `get_ok()` called for real against the live CLOB (unauthenticated, safe), the failure-counter/halt/resume state machine exercised directly with a fake client, and the balance-snapshot/halt logic exercised directly with a fake balance response — a real ghost fill can't be manufactured for a test, so that specific path is verified structurally, not proven against an actual silent on-chain fill.

## Key gotchas

- **5-minute market discovery** (`btc_5m_market_finder.py`): Polymarket appears to batch pre-create a full day's worth of future 5-min windows in advance. Asking Gamma for "most recently created" markets surfaces *tomorrow's* freshly-created placeholder windows, not today's genuinely-about-to-close one. The fix already in place: compute the expected slug (`btc-updown-5m-<epoch>`, epoch always a multiple of 300) directly from wall-clock time and look it up, rather than sorting/filtering a list. Also: don't trust Gamma's `closed` flag for these fast-cycling markets — it lags actual resolution; status is derived from epoch vs. wall clock instead.
- **Zero-drift probability model** (`oracle_lag_strategy.py`): the Brownian-motion model deliberately assumes zero drift. Over a 5-minute horizon, real trend is swamped by noise, and zero drift keeps the estimate a pure martingale with no built-in directional bias — the actual edge comes from seeing the price before the market/oracle does, not from predicting direction.
- **Quarter-Kelly default**: `kelly_multiplier=0.25` is deliberate, not conservative-for-its-own-sake — the probability model is an approximation, not a known-true probability, so full Kelly would be overconfident. `max_position_pct` is a separate hard cap independent of what Kelly suggests.
- **CLOB clock skew**: `preflight_check.py` checks skew against the CLOB server explicitly because Level-2 auth signatures are timestamp-sensitive (PASS ≤10s, WARN ≤60s, FAIL >60s). If CLOB auth is failing mysteriously, check this first.
- **Allowances are read live, not computed locally**: `preflight_check.py` and `approve_usdc.py` both fetch current USDC spender allowances from `get_balance_allowance` rather than hardcoding exchange contract addresses — the addresses returned by that live endpoint don't match what's bundled in `py_clob_client`'s local config, so hardcoding would be wrong.
- **Trade settlement source of truth**: `paper_trader.py` prefers Polymarket's own Gamma API resolution (`outcomePrices`) over the bot's own price-based guess. Only falls back to comparing last-known price to the window anchor after `SETTLE_FALLBACK_AFTER` (120s) with no Gamma resolution — and flags that fallback explicitly (`resolution_source: "price-fallback"` vs `"gamma"`) so it's never silently conflated with a real settlement.
- **`trades.csv` is a post-trade blotter, not a lifecycle log**: one row per trade, appended only once it resolves (entry+fill+exit+resolution together). Open positions are visible live via `paper_state.json` instead — don't try to append an "OPEN" row to `trades.csv` for a new trade type; follow the existing pattern.
- **`.env`** is loaded automatically by scripts that need it (via `python-dotenv`, resolved relative to the project root regardless of cwd) — real environment variables still take precedence over it.
- **`resolve_market_outcome()` lives in `btc_5m_market_finder.py`**, not in `paper_trader.py`/`live_trader.py` — both bots import and call the same function so settlement logic can't silently drift between them. Add any future settlement-source changes there once, not per-bot.
- **Pidfile-based single-instance protection**: both bots call `pidfile.claim_or_exit()` at startup and exit immediately if another instance is already alive per their pidfile. This is deliberate for `paper_trader.py` too (not just `live_trader.py`) — two paper bots sharing one state file would corrupt it just as surely as two live bots sharing one wallet would double-trade it.
- **Order book ask ordering** (`/book` from `clob.polymarket.com`): `asks` comes back sorted **descending** (worst price first, best/lowest price last) — the opposite of what a naive `asks[:N]` read would assume, and the opposite of `bids`' own ordering (ascending). `gabagool_strategy.py`'s book-walking code re-sorts explicitly rather than trusting response order; check this again if you write anything else that reads `/book` directly.
- **Gabagool's fee formula is load-bearing, not a footnote**: `fee = shares * fee_rate * price * (1 - price)`, taker-only, `fee_rate = 0.07` for crypto-category markets — verified against `docs.polymarket.com/trading/fees.md` and the live `/fee-rate` endpoint, not assumed from the reference repo's threshold. This fee is symmetric around 50¢ and *maximized* there, which is exactly where a crossed book is most likely to appear — a fee-blind "sum < $0.975" filter (the reference repo's own rule) can and does approve trades that are a guaranteed net loss. If this fee schedule ever changes, `gabagool_strategy.py`'s `--fee-rate` flag needs updating, not just its default.
- **`gabagool_paper_trader.py` lives in `paper_trading/`, not its own directory**: it was originally built as a fully siloed `gabagool_bot/` bot with its own dashboard, then folded in once the dashboard grew to manage three paper strategies in parallel — colocating it means one dashboard, one `sys.path` pattern, one `BOT_SCRIPTS`/`bots` registry to extend. It still shares no state or logic with `paper_trader.py`: separate state file, trades log, and pidfile, and a completely different (non-Kelly, non-directional) engine.
- **Additive vs. multiplicative entry filters are genuinely different math, not two names for the same thing**: v1's `--min-edge` is additive (`p_true - price >= threshold`); v2's `--safety-factor` is multiplicative (`price <= p_true * factor`). They diverge sharply away from p=0.5 — at p=0.90, `min_edge=0.02` allows paying up to 0.88, but `safety_factor=0.85` only allows paying up to 0.765. Don't conflate them when reasoning about either engine's behavior, and don't assume tightening one tightens the other.
- **Compounding bankroll design (`oracle_lag_strategy_v3.py`)**: `OracleLagEngineV3.set_bankroll_provider()` deliberately takes a callback returning the caller's **absolute** current bankroll, not a P&L delta to add to the initial value. Reason: `PaperTrader`/`LiveTrader.stats()['realized_pnl']` is summed from an in-memory `closed_positions` list that, on process restart, is rebuilt only from the state file's capped `recent_closed` tail (last 25) — a delta fed by that figure would silently understate the true bankroll after any restart following more than 25 closed trades. `PaperTrader.equity()` (`cash` + open-position stakes) sidesteps this entirely since `cash` is restored verbatim from the state file, so `paper_trader.py` wires `engine.set_bankroll_provider(trader.equity)` directly. `LiveTrader` has no equivalent restart-safe running balance to read back locally, so its `equity()` (`--bankroll` + `realized_pnl`) is stuck with the same restart-window caveat as a fallback — documented in its own docstring, not silently assumed away. Bankroll is floored at 0 before being handed to `KellySizer` either way, so a provider that (temporarily) returns negative never produces a negative stake.
